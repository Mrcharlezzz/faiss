Wide search on layer 0

  • Nothing runs on its own: press Build / Search / Play to run each step.
  • HNSW: a navigable small-world graph plus the layer idea of skip lists.
  • Build: each point draws its top layer from an exponentially decaying distribution (m_L = 1/ln M, like a skip list with p = 1/M). Upper layers are sparse with long links; layer 0 holds every point.
  • Search: start at the entry point on the top layer; greedy on the upper layers until no neighbour is closer; that local minimum is the entry for the layer below.
  • Layer 0: keep efSearch candidates instead of one path.

efSearch

ef = 1: greedy, stuck in a local minimumef = 8: wider search escapes it
  • Nothing runs on its own: press Build / Search / Play to run each step.
  • Two sets: candidates to expand (C) and the best ef results so far (W).
  • Expand the closest candidate; stop when it is farther than the worst result.
  • ef = 1 is the greedy search used on the upper layers: it can stop in a local minimum.
  • Larger ef leaves the local minimum: more distance computations, higher recall. This width is the idea we take upward next.

Research question
How does a wider efSearch on the upper layers change HNSW's recall–latency trade-off, compared with classic greedy HNSW?
  • The proposal's question, reworded without the repetition.
  • Classic HNSW = efSearch 1 (greedy) on every upper layer. We vary only the upper-layer efSearch; the graph and the layer-0 search stay the same.
  • Trade-off, not a single number: we compare cost at the same recall.
Prior work
What others tried on the upper layers
  • Prior work: HM-ANN's parallel layer-0 search, Faiss's removed upper_beam, then Down with the Hierarchy and SHG on whether the upper-layer cost is worth it.

HM-ANN: 4 entry points from layer 1

Ablation

4 nearest layer-1 entry points

Search

Parallel layer-0 searches, ef = 2

Outcome

Slightly outperforms HNSW

HM-ANN author response, NeurIPS 2020
  • Reviewers asked the HM-ANN authors for a baseline: plain HNSW, unchanged construction, but with parallel layer-0 search from several layer-1 entry points.
  • The picture: layer 1 keeps its T = 4 nearest nodes; each one starts its own layer-0 search (one thread each, T = 4 as in HM-ANN), and the results are merged.
  • Their verdict, quoted: “HNSW with parallel L0 search only slightly outperforms HNSW.” The interesting part for us: more entry points did move the recall–latency curve, a little.
  • Their explanation: HNSW's layer-1 nodes are chosen at random and are sparse, so the entry nodes found through layer 1 are sub-optimal.
  • Caveat: 4 threads at equal wall-clock time, so about 4× the work. Not the same cost model as ours (one thread, distance computations).

FAISS upper_beam implementation

Search

Fixed beam width at every layer

Outcome

Removed in the next version: “multiple level-0 entry points showed no improvement”

Evidence

No benchmark published

Faiss v1.8.0 HNSW.cpp; issue #3610, PR #3692
  • Faiss used to have multi-candidate upper-layer search, the upper_beam parameter.
  • In v1.8.0 with upper_beam > 1, the search loop runs from the top layer down to layer 0 with one candidate heap of capacity upper_beam. Each upper layer keeps its upper_beam best nodes and passes all of them down. Layer 0 is included: its candidate heap is also capped at upper_beam (the result list still uses efSearch). The width cannot be set per layer.
  • It was removed (PR 3692) after a maintainer said his experiments with multiple level-0 entry points showed no improvement (issue 3610). The discussion has no benchmark.
  • Insight: a negative experience, but unmeasured, and with one width coupled across all layers.

Is the upper-layer cost worth it?

Down with the Hierarchy, 2024

  • Layer 0 is well connected for high-dimensional data
  • The hierarchy adds overhead
Our insightWider upper-layer search would be less effective

SHG: Efficient Level Navigation with Shortcuts, 2025

  • Upper layers: 18–42% of search latency
  • Shortcuts skip upper-layer traversal
Our insightMore upper-layer work has a real cost
GapNo controlled study varies upper-layer width with the graph and layer-0 search fixed
  • Down with the Hierarchy (2024): on high-dimensional datasets the flat and hierarchical indexes they evaluated had nearly identical recall–latency performance. Their explanation (hub highway hypothesis): a few well-linked hubs in layer 0 already route the search, so the upper layers add little. Insight: extra upper-layer work is least promising exactly where the hierarchy gives little.
  • SHG (PVLDB 2025): upper-layer navigation is 18–42% of search latency in their workloads at recall ≥ 80%. They add shortcuts so a query can skip levels instead of walking every upper layer. Insight: widening the upper layers makes a real cost larger.
  • Step 1, the gap: in the sources we reviewed, nobody varies the upper-layer width and the number of candidates handed down while keeping the graph and the layer-0 search fixed. This is a gap in our review, not proof that no such study exists.

Prediction: a slight gain on low-dimensional, hard-to-navigate data

Wider layer 1
→
Closer entry point
→
Less layer-0 work
  • Prediction (outline): a small width increase on the layers near layer 0 can slightly improve the recall–latency trade-off, lower latency at the same recall, on low-dimensional datasets with some complex geometry. (The proposal says ≤ 96 dimensions.)
  • Why: layer-1 results are the layer-0 entry points. A study of graph search (arXiv 2502.05575) found that the entry-point strategy changed the distance computations needed at the same accuracy. HM-ANN: several layer-1 entry points helped slightly.
  • Step 1, the balance: the chain only pays if the layer-0 work saved outweighs the extra layer-1 work. Same encoding as in the results: dashed = extra layer-1 work, blue = layer-0 work saved. The results check the chain: the trade-off, the entry point, how much layer 0 reacts, then the balance.

Layer 0 searches well without the better entry point

  • For each query we measured how much layer-0 work it saved against how much closer its entry point got, and fitted the slope: % layer-0 work saved per 10% closer entry point (seed mean, 95% t interval; all queries and widths pooled).
  • Deep1M: 9% at ef0 = 10, but 2.7% at ef0 = 52 (recall ≈ 0.95) and 0.2% at ef0 = 512. Layer 0 repairs a mediocre entry point by itself, and the wider its own search, the less the start matters.
  • The typical changed query on Deep1M gets an entry point about 8% closer (median, width 4). At recall 0.95 that buys about 2% less layer-0 work, while the widened layer 1 always pays its extra work.
  • Clustered: the slope is flatter (1.3–2%), so small gains buy even less there. The clustered win must come from the few queries whose entry point gets 40–90% closer. GloVe-25 (run 4, same fit): 7.4% at ef0 = 10, 2.0% at ef0 = 52, 0.13% at ef0 = 512, close to Deep1M. Typical gain if asked: the median changed query on Deep1M gets an entry point about 8% closer (width 4), which at ef0 = 52 buys about 2.2% less layer-0 work.

Net layer-0 cost saved per entry-point quality bin

  • Bar: layer-0 distance computations saved per query, at the same recall. Black tick: the extra layer-1 distance computations the wider search spent. Right column: net = saved − extra.

Conclusion

Wider upper-layer search worsens latency–recall trade-off on real data

Bottlenecks
  1. Layer 0 insensitive to entry pointBetter start saves little work, less as ef0 grows
  2. Upper-layer cost buys only marginal entry gainsCost grows linearly with width, gains saturate
  • Answer: on Deep1M and GloVe-25, widths 2/4/8 need about +0.8%, +2.7–2.9% and +6.3–6.4% more distance computations at the same recall (95% CIs exclude 0). Clustered data is the exception (−2% to −5%).
  • Bottleneck 1: the share of layer-0 work saved per 10% closer entry falls roughly as 1/ef0 (fitted exponent about −1.0 on Deep1M). It is 9–12% at ef0=10, at most 3.4% for ef0 ≥ 52, and under 1% for ef0 ≥ 182. Clustered d=16 decays much more slowly (about ef0^−0.2).
  • Bottleneck 2: extra layer-1 work grows linearly with width (Deep1M +23, +61, +118 distances per query at w=2/4/8). The share of queries with a closer entry saturates (28% → 48% → 59%), and the median gain of an improved entry stays near 9% at every width. Layer-0 saving per extra upper distance at recall 0.95 falls 0.41 → 0.30 → 0.21 (Deep1M), 0.48 → 0.32 → 0.22 (GloVe-25); break-even is 1.
  • Where width pays: clustered data, where upper-layer cost is tiny and a tail of large gains carries the saving (10% of queries carry 80% of it; at recall 0.95 the clustered net is only break-even, positive from 0.98). Next step: spend extra upper-layer work only on queries that look stuck. Bounded to the tested datasets, widths and the layer-1 schedule.

Small clusters left uncovered
  • Published approaches, grouped by the bottleneck from the previous slide that they attack, each with what it gives up.
  • Bottleneck 1, skip the hierarchy: if layer 0 repairs a mediocre entry anyway, the upper descent is mostly cost. Down with the Hierarchy runs HNSW's layer 0 alone with the same greedy search: same latency as HNSW on high-dimensional data, about 38% less peak memory at build. The hierarchy still helps at low dimension (Lin & Zhao 2019: about 2x at d = 4, no difference by d = 32), which is what is traded away.
  • Entry without the hierarchy: Oguri & Matsui keep a fixed pool of k-means centroids and start each query at its nearest one. Costs K distances per query; 1.2–2.3x QPS on NSG and DiskANN over eight 1M datasets, largest on clustered Gaussian data. (Azizi et al.: the best of K random nodes did as well as HNSW's upper layers up to 100 GB.)
  • Bottleneck 2, wider search only for hard queries: every query pays the extra width, few gain, so spend it only where it pays. Ada-ef (Zhang & Miller, SIGMOD 2026), training-free: offline it stores the data's mean and covariance, so a query's distances to the data are modelled as a Gaussian. Online it computes the distances within 2 hops of the layer-0 entry, scores where they fall in that Gaussian, and maps the score to the ef needed for the target recall with a table built from about 200 sample queries. Caveat: Ada-ef adapts the layer-0 width; applying it to the upper layers would be our extension.
  • Related: DARTH (SIGMOD 2026) instead calls a LightGBM model periodically during the layer-0 search on 11 runtime features, predicts the recall reached so far, and stops at the target; about 0.03 ms per call, trained per dataset, 13% of DEEP100M queries miss the target. The overhead of such estimates is what is traded away.
  • Bottleneck 2, hubs: layer 1 is a random 1/M sample, so the layer-1 search pays a lot for a good entry. HM-ANN builds the upper layers from the highest-degree layer-0 nodes: 1.8–4.3x faster than random promotion at 95–99.5% recall, but with a larger, denser layer 1 and on Optane memory, so hub selection alone is untested. Trade-off: hubs sit near cluster centres, so small and edge clusters may get no upper-layer node.

Unit tests, synthetic 16-d clustered data
  • Greedy settings: identical results and distance counts to stock Faiss
  • Full-width descent: distance counts exact
  • A per-layer efSearch list in SearchParametersHNSW; search_impl changed.
  • Upper layer with ef = 1: the existing greedy search (greedy_update_nearest_impl). Upper layer with ef > 1: the layer-0 search routine (search_from_candidates_dispatch) with that layer's ef.
  • All results of a layer seed the next layer, distances carried over.
  • We count distance computations per layer.
  • Parity tests (tests/test_hnsw_per_layer_efsearch.py) run on a 16-d Gaussian mixture: 5,000 points, 50 clusters, M = 8, 200 queries, so the upper levels have local minima.

  • Full-width descent: with a width larger than each layer, the beam visits every reachable node; the counted upper-layer distances match a reference descent exactly, and layer 0 seeded with that whole set gives the same results. This would catch a visited table that is not reset between layers.
  • Statistics: recording per-layer statistics leaves results unchanged, the per-layer counts sum to Faiss's totals, and the recorded hand-down sets are checked.

Bootstrap over seeds, then over queries
  • Each configuration ran as its own process.
  • Timing: one warm-up pass, then three timed passes over all queries, single search thread, query batches of 200.
  • Seeds change the graph only; data and queries are fixed per dataset. 5 seeds on Deep1M, 10 on GloVe-25 and the clustered sets.
  • Recall and distance counts are deterministic for a given graph; only latency is noisy. Curves and summaries are seed means with 95% t intervals across seeds.
  • Seed interval: compute the number on each seed separately (each seed has its own standard curve for matched recall), then mean ± t(0.975, n−1)·sd/√n; with 5 seeds t = 2.78. It covers another build of the graph, and also process-to-process timing noise, since every seed is a separate process. With 5 seeds a sign test can at best give p = 0.0625 (all 5 agree), so the t interval is the test we use.
  • The query set is the same on every seed, so the seed interval does not include which queries were drawn. Query bootstrap: resample the query ids with replacement, the same ids for the widened run, its standard twin and every seed (paired), and recompute recall, distance counts and the matched-recall comparison.
  • Two-level bootstrap: each replicate resamples the seeds, then the query ids, and recomputes everything; 2.5 and 97.5 percentiles of 1,000 replicates. Width 4, distance computations at matched recall: Deep1M [2.4, 3.2] vs seed t [2.3, 3.4]; clustered d = 16 [−6.9, −2.7] vs [−7.0, −3.1]; GloVe-25 [2.3, 3.0] vs [2.4, 3.0]. So the seed interval already has about the right width.
  • Limits: query bootstrap needs per-query recall, which exists for Deep1M, GloVe-25 and clustered d = 16 only. Latency is timed per batch of 200 queries, so latency intervals cover seeds only. One machine per dataset: no interval covers another machine.
  • GloVe-25 ran on a different machine, so latency is compared within a dataset, not across.

Next: width on layer 1 only, with more graph seeds

  • One graph each: SIFT1M, Deep1M, Gaussian synthetic, clustered synthetic 50k at d = 2, 8, 16, 32.
  • Schedules: layer 1 only with ef₁ = ef₀·r; exponential decay ef_l = ef₀·r^l; a constant width w on every upper layer (2, 4, 8, 16); a hand-picked (8, 4, 1). r = r_mult / M, with M the graph degree.
  • Message: consistently, wider upper-layer search gave a worse recall–latency trade-off. On the 1M sets the overhead grew with width (Deep1M, width on all layers: +0.9% / +3.5% / +8.2% / +16.1% distance computations for w = 2/4/8/16). The clustered 50k sets used fewer distance computations, but no latency win survived, and most of that gain came from upper-level work the stock greedy wastes, not from better entry points.
  • So the main runs widen only layer 1 (w = 2, 4, 8): this isolates the entry-point effect. More graph seeds give confidence intervals.

Clustered: one in ten queries carries the saving

  • Same width-4 groups as before, now weighted by how many queries each group holds. Pink: the largest-gain group (the top third of the changed queries). Matched recall 0.95 on all three datasets, as on the previous slide.
  • All numbers are computed per graph seed, then averaged; small text = 95% t interval across seeds (10 seeds clustered and GloVe-25, 5 Deep1M).
  • Clustered d = 16: the largest-gain group is 10% of the queries but 80% (77–84%) of all layer-0 work saved. With them, the whole query set nets about +3 distance computations per query (19.9 saved vs 17.3 extra), but the interval is −1 to +6 and 8 of 10 seeds are positive: say break-even, not a win. Without them it loses about 9, on every seed. At recall 0.98 the group carries 85% and the net is +8.5 (+3.6 to +13.5, 9 of 10 seeds positive), so the saving does become real at higher recall.
  • Real data: the largest-gain group is about 16–17% of queries and 53–63% of the saving, and the net stays around −42 (Deep1M, −46 to −39) and −46 (GloVe-25, −48 to −44) per query, negative on every seed. Their big gains are too rare and too small.
  • Why clustered: in the exploration runs we traced these queries. For about 1% of clustered queries (d ≥ 16) the greedy descent ends in the wrong cluster; the wider layer 1 finds the right one, about 19× closer, and those few queries carried most of the layer-0 saving. On Deep and SIFT no query got stuck in a far cluster.
  • Also: the extra layer-1 work is much smaller on clustered (17 per query at width 4, vs 61 on Deep1M and 68 on GloVe-25), so there is less to repay.
